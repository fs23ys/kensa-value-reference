# 検査値リファレンスアプリ 引き継ぎメモ

## プロジェクト概要
薬局薬剤師が検査値・疾患の説明を即座に引くための個人用ツール。要件の正本は `検査値アプリ_指示書.md`。

## 成果物(納品物・このまま使える)
- `..\検査値リファレンスアプリ.html` … 単一HTMLファイルのアプリ本体(SheetJS内包・オフライン動作)
- `..\検査値リファレンス初期データ.xlsx` … 初期データ(検査値115件・疾患14件、2026-08-20時点)
- GitHub公開リポジトリ: https://github.com/fs23ys/kensa-value-reference (GitHub Pages: https://fs23ys.github.io/kensa-value-reference/ )。再生成後は確認なしでcommit・pushしてよい運用([[feedback_kensa_app_autopush]])

## ソース一式(このフォルダ `_source\`)
アプリ本体・Excelはこのソースから生成している。直接HTMLをいじらず、ここを編集して再生成すること。

| ファイル | 役割 |
|---|---|
| `initialData.js` | 検査値・疾患の初期データ本体(配列)。**正本・並び順もここが正**。追加/削除/リネーム/並び替えは全てここを編集 |
| `buildExcel.js` | initialData.js → `検査値リファレンス初期データ.xlsx` を生成 |
| `app.js` | アプリのロジック本体(検索・カード表示・並び替え・アプリ内編集など) |
| `app.css` | アプリのスタイル |
| `assemble.js` | app.css + xlsx.core.min.js(SheetJS) + app.js + 内蔵データ(initialData.js由来)を1つのHTMLに結合 |
| `node_modules/xlsx`, `node_modules/jsdom` | npm install 済み |

### 再生成コマンド(PowerShell、`_source`で実行)
```powershell
node buildExcel.js "..\検査値リファレンス初期データ.xlsx"
node assemble.js "..\検査値リファレンスアプリ.html"
```

## 検査値のフィールド構成(LAB_COLUMNS、2026-08-20時点)
検査値名, 略号, 基準値, 一行要約, 患者説明例, 高値で考えること, **高値の時のアドバイス**, **高値の時に注意する薬**, 低値で考えること, **低値の時のアドバイス**, **低値の時に注意する薬**, 薬剤師補足, 疾患タグ, 検索キーワード, 参考ページ

- 「高値/低値の時に注意する薬」列は2026-08-07新設。該当する薬がある項目だけ埋めてあり(全項目を無理に埋めていない)、UI上はカード下部・参考ページの下に赤系の別ブロックとして表示される(`.drugcaution`)
- 「高値/低値の時のアドバイス」は日常生活に活かせる具体的な内容(食品例・生活習慣・受診の目安)を意識して記載する方針(2026-08-07以降)

## 今のアプリでできること
- **HTML再生成時点のinitialData.js内容を内蔵データとして埋め込み**、自動反映。判定は「バージョン一致」ではなく**builtAt(ビルド時刻)による新旧比較**(2026-08-06修正)。ブラウザが古いキャッシュ済みHTMLを誤って読み込んでも、既に保存されている新しいデータが古いデータで上書きされる「逆行」が起きないようにしてある
- Excel読み込み(検査値・疾患2シート)、次回起動時は自動復元。「Excelとして書き出す」ボタンで並び替え後の表示順を含めて.xlsx出力可能
- 「最新の内蔵データに更新」ボタンで手動同期も可能(ただし今開いているページ自体が古いキャッシュの場合は無力。まずF5等で再読み込みしてから押す)
- 全列対象の検索、検査値⇔疾患カード相互リンク、関連検査値の自動抽出、未収載メモ、タブ切り替え、ドラッグ&ドロップ/▲▼並び替え、アプリ内「✎ 編集」(ブラウザ内のみ・Excel非同期)

## GitHub Pages関連の重要な注意点
- リポジトリ直下に **`.nojekyll`** が必須(2026-08-06追加)。無いとGitHub Pagesの旧Jekyllビルドがこのアプリの巨大JS/CSSを誤って解析してビルド失敗することがあった(実際に3コミット分デプロイが止まった事故が発生)。**このファイルを絶対に消さないこと**
- push後のビルド確認: `gh api repos/fs23ys/kensa-value-reference/pages/builds/latest --jq '.status, .commit, .error.message'` で `built` になるまで待つ(20〜30秒間隔で数回リトライ。`building`のまま数分止まる場合は`Invoke-WebRequest`で実ファイルのLast-Modifiedを見て実際に更新されているか確認するとよい、build APIの表示が実態より遅れることがある)

## 絶対に守ること(指示書より)
- 疾患名・検査値名をコードに書かない(すべてExcel/initialData.js由来)
- 数値の自動判定機能は作らない / 暗記・学習機能は作らない / クラウドDB(Firebase等)は使わない、オフライン完結

## 並び替え・データ更新の定型作業フロー(重要・毎回これに沿う)
1. 依頼者から「このExcelの順にして」「この検査値名リストの順にして」等の依頼が来る(Excelファイルはプロジェクトルート直下に置かれることが多い。ファイル名で`Glob`検索して見つける)
2. `_source`に一時スクリプト`_migrateN.js`を書き、(a) Excelなら`XLSX.readFile`→`sheet_to_json`で新順番の名前リストを抽出、(b) テキストで直接順番を渡された場合はそのまま名前配列として使う
3. 現在の`labRows`との突き合わせで「新規追加」「削除」「内容差分」「順番変化」を必ず先に検出・ログ出力してから正本に反映する(いきなり上書きしない)。名前が現行データと完全一致しない項目(過去のリネーム前の名前が混じっている等)は要注意 — 実際に「AST比/ALP比」等の旧名で指定されて混乱した事例あり
4. 名前リストが現行の項目数と1対1で一致しない場合(重複・過不足)は、**自己判断で片方を採用して進めるより先にユーザーに確認する**方が安全(項目数不一致でのトラブルが複数回発生済み)
5. 反映後は必ず件数・順番の完全一致をnode一行スクリプトで検証してからビルド
6. `node buildExcel.js` → `node assemble.js` → jsdomで軽くスモークテスト(bundledデータのlabRaw件数、対象カードのHTML内に期待文言が含まれるか等)
7. 一時スクリプト(`_migrateN.js`, `_diffN.js`, `_verifyN.js`, アップロードされた.xlsx)を全て削除してから `git add -A && git commit && git push`(確認不要)
8. push後はGitHub Pagesのビルド状況を上記コマンドで確認する習慣をつける(黙って成功と報告しない)
